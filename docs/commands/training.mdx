<Warning>
Set `HF_TOKEN` first (Gemma-3-270M is gated) — and if you want live checkpoint upload
(on by default) or W&B logging, set those in the SAME shell/cell too, not a separate
`!export` cell on Kaggle/Jupyter (that doesn't persist to a later cell's subprocess):
```bash
export HF_TOKEN=hf_...          # WRITE access — needed to fetch Gemma-3 AND to push checkpoints
export WANDB_API_KEY=hf_...     # optional — enables live train/val/test charts
export PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True   # reduces CUDA memory fragmentation
```
</Warning>

## 1 · Fetch training data

Each phase has its own focused fetch script, pulling straight into the local layout the
trainers read — see [Full cheatsheet](/commands/cheatsheet) for more on both.

<Tabs>
<Tab title="Phase 1">
Lands already Mimi-encoded (Parquet shards unpacked into `.npz` + frame records) — ready
to train immediately, no encode step:
```bash
python scripts/20_fetch_phase1.py
```
```bash
python scripts/20_fetch_phase1.py --repo <user>/<repo>   # a different repo than the default
```
</Tab>
<Tab title="Phase 2">
Lands as raw audio + full scenario schema — needs a local encode + frame-build pass
first (fast, free, no API calls):
```bash
python scripts/21_fetch_phase2.py

python scripts/00_encode_audio.py --audio-dir data/audio --out-dir data/encoded
python scripts/04_build_frames.py --in data/scenarios/scenarios_all.jsonl \
    --frames-out data/frames/frames_all.jsonl
```
Fetches whichever repo layout is present — the current Parquet-shard layout
(`data/phase2-shard-*.parquet`) or the older loose per-clip layout — and unpacks either
into the same local `data/audio/` + `data/scenarios/scenarios_all.jsonl`.
</Tab>
</Tabs>

<Warning>
**Real observed problem, fixed:** the loose per-clip Phase-2 layout (one `.wav` + one
`.json` per clip, bucketed into 200 folders) took **minutes per folder** to fetch — almost
entirely per-request round-trip latency across thousands of tiny files, not bandwidth
(the download itself was also needlessly capped at 4 concurrent files — bumped to 32 by
default, override with `HF_FETCH_WORKERS`).

The real fix: repack the repo into a handful of self-contained Parquet shards (audio
bytes + timestamps + the full scenario record embedded per row — no separate files to
join), same idea as Phase-1's shards. One-time conversion, safe to run on a small CPU box
(no GPU/Mimi needed — this never touches audio content, just repackages files) since it
processes the 200 upload folders in bounded batches, one shard at a time, never holding
more than one batch on disk:
```bash
export HF_TOKEN=hf_...
python scripts/23_repack_phase2_to_parquet.py --dry-run   # see the batch/shard plan first
python scripts/23_repack_phase2_to_parquet.py             # convert (resumable)
```
Verify with `scripts/21_fetch_phase2.py`, then reclaim repo space (deletes only the OLD
`audio/`/`timestamps/` folders — `scenarios/`, the new `data/*.parquet`, metadata, and
README are untouched):
```bash
python scripts/23_repack_phase2_to_parquet.py --delete-old
```
Verified offline with a full round-trip test through the real conversion code: wav bytes,
timestamps, and scenario records come back byte-exact, and re-fetching is idempotent (no
duplicate scenario lines).
</Warning>

## 2 · Train

Two ready-made configs per phase — pick the one matching your GPU. The big-GPU configs
apply real, verified optimizations (see the warning below the table) beyond just a
bigger batch size.

<Tabs>
<Tab title="L4 (24GB)">
```bash
# Phase 1 — modality alignment (LoRA):
python scripts/06_train_phase1.py --config configs/train_phase1.yaml \
    --frames "data/frames_phase1/*.jsonl"
```
```bash
# Phase 2 — referee fine-tune (full bf16), warm-started from Phase 1:
python scripts/07_train_phase2.py --config configs/train_phase2.yaml \
    --frames "data/frames/*.jsonl" \
    --init artifacts/thinkspark-v2-350m/phase1/runs/<run-id>/final/model.pt
```
`configs/train_phase{1,2}.yaml`: `batch_size: 4`, `grad_accum: 16` (effective batch 64),
`grad_checkpointing: true` — sized to fit a 24GB card without OOM (a real batch_size 16
run OOM'd outright: Gemma-3's 256K-vocab cross-entropy tensor alone needs ~9GB at that
size).
</Tab>
<Tab title="H100 / H200 / RTX6000 / Blackwell (80GB)">
```bash
# Phase 1:
python scripts/06_train_phase1.py --config configs/train_phase1_bigGPU.yaml \
    --frames "data/frames_phase1/*.jsonl"
```
```bash
# Phase 2, warm-started from Phase 1:
python scripts/07_train_phase2.py --config configs/train_phase2_bigGPU.yaml \
    --frames "data/frames/*.jsonl" \
    --init artifacts/thinkspark-v2-350m/phase1/runs/<run-id>/final/model.pt
```
`configs/train_phase{1,2}_bigGPU.yaml`: `batch_size: 48`, `grad_accum: 1` (one
forward/backward per step, no accumulation loop), `grad_checkpointing: false` (you have
the VRAM — this alone is a large speedup), TF32 matmuls, SDPA attention, 8 dataloader
workers with pinned memory. Phase-1 is 1 epoch (still a full, legitimate alignment pass
over ~400h — bump to 2 if you have time to spare); Phase-2 stays 3-5 epochs per the
recipe (smaller corpus, needs more passes).
</Tab>
</Tabs>

<Warning>
**The real speed win, on every config, every GPU:** the LM head only needs to run on the
spoken-tail positions actually supervised by the loss (everything else is
`ignore_index=-100`) — not the whole ~1000-token sequence. The model requests only that
tail via transformers' native `logits_to_keep`, cutting the single most expensive
op (a 256K-vocab head) by ~5-10x. **Verified bit-identical loss** to the full computation
offline (diff `0.00e+00`) — zero quality cost, pure speedup. Falls back to the full
computation automatically if a transformers version doesn't honor the parameter.

`torch.compile` is deliberately **off** in both big-GPU configs — a real, confirmed
incompatibility on current transformers: combining `output_hidden_states=True` with
LoRA/PEFT under Dynamo raises `KeyError: 'hidden_states'` mid-graph, not at compile time.
If you re-enable `compile: true` after a library upgrade, the trainer self-heals a
runtime break on the first batch by falling back to eager rather than crashing the run —
but verify a few steps before trusting a long run.
</Warning>

## Runs, resume, and live checkpoint upload

Every invocation is a **run** (own id, own checkpoint folder). Checkpoints save every
`save_every` steps (model + optimizer + exact epoch/step position) and, unless
`--no-push`, upload **live during training** to `<phase>/runs/<run-id>/<tag>/` on the
model repo (default `anuj-inavlabs/kupe-thinkspark-audio-270m`) — so an interrupted run
resumes from HF even on a fresh box.

```bash
# force a brand-new run from step 0 (ignores any existing checkpoint for this run-id):
python scripts/06_train_phase1.py ... --fresh

# resume a specific run — local checkpoint if present, else pulled from HF automatically:
python scripts/06_train_phase1.py ... --run-id 20260830-101500 --resume

# train without uploading anything (local checkpoints only):
python scripts/06_train_phase1.py ... --no-push
```

`--init` (Phase 2 only) warm-starts from a Phase-1 checkpoint, but is ignored when
`--resume` restores this Phase-2 run's own weights instead.

**Manual push** (outside training, e.g. after the fact):
```bash
python scripts/22_push_checkpoints.py --ckpt-dir artifacts/thinkspark-v2-350m/phase1 --phase phase1 --all
```

## Watching it train

Terminal loss curves print every `log_every` steps (via `plotext` if installed) — the
reported loss is the TRUE value averaged over the full effective batch (all
`grad_accum` micro-batches), not a single noisy micro-batch:
```
[P2] epoch 1 step 340/2000 lr=8.4e-05 loss=1.2841 ctrl=0.712 txt=0.401 vap=0.171
```

**Weights & Biases** (set `WANDB_API_KEY`, `wandb_project` in the config): live charts
for train loss + every component + LR, a full **validation** eval every `eval_every`
steps and at each epoch end (2% of data held out, `val_frac`), and one final **test**
eval at the very end (1% held out, `test_frac`) — the honest generalization number, never
touched during training. Compare `train/loss` vs `val/loss` on the dashboard: they
tracking together and both falling is healthy; `val/loss` rising while `train/loss` keeps
falling is overfitting.

## Tuning knobs (`configs/train_phase{1,2}[_bigGPU].yaml`)

| Field | What it controls |
|---|---|
| `batch_size` / `grad_accum` | effective batch = batch_size × grad_accum |
| `grad_checkpointing` | trade compute for memory; turn off on a big GPU for speed |
| `use_lora` | `true` for Phase 1, `false` (full fine-tune) for Phase 2 |
| `adam_beta1` / `adam_beta2` | AdamW betas — default (0.9, 0.95), the LLM-pretraining/Moshi default |
| `label_smoothing` | optional (0-0.1) extra regularization on the text CE |
| `lambda_ctrl` / `lambda_txt` / `lambda_vap_p2` | Phase-2 loss weights (default 1.0/0.5/0.2) |
| `focal_gamma` | focal-loss sharpness on the control head (default 2.0) |
| `frame_drop_aug` | fraction of frames randomly dropped for robustness (default 5%) |
| `val_frac` / `test_frac` / `eval_every` | held-out eval splits + cadence |
| `wandb_project` / `wandb_entity` | set to enable W&B; `null` disables |
| `num_workers` / `compile` / `attn_implementation` | dataloader workers, torch.compile, sdpa/flash_attention_2 |
| `ddp` | set `true` when launching with `torchrun` |

Optimizer weight decay applies only to real matmul weights, never to biases,
norm scales, or embeddings — the standard LLM/Moshi practice, not decaying those.
